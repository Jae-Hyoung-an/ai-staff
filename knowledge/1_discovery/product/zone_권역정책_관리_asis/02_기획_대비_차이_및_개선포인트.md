## 요약 (So What)

실제 화면을 기존 기획 문서와 대조한 결과, **문서-구현 간 불일치 3건**과
**화면 자체의 개선 이슈 8건**을 발견했습니다.

우선순위가 가장 높은 것은 **용어 통일**입니다. 같은 필드를 화면마다 다른 이름으로
부르고 있어서, 운영자가 값의 의미를 확신할 수 없고 기획 문서와도 매칭이 안 됩니다.
용어를 정리하면 아래 이슈 중 3건(#1, #2, #5)이 자연히 해소됩니다.

## Part 1. 기획 문서 대비 차이 (문서-구현 불일치)

### 차이 1. 슬롯 시간대가 문서·구현·기본값 3개가 모두 다름

용어집(`01_용어집.md` "슬롯 구분")은 슬롯 시간대를 고정값처럼 정의하고 있지만,
실제 화면은 **정책별로 자유 입력**이며 값도 다릅니다.

| 슬롯 | 용어집 (기획) | 성북 1 zone (실제 운영) | 생성 화면 기본값 |
|------|--------------|------------------------|-----------------|
| 1 | 아침 `07:00~11:00` | 아침 `09:00~10:55` | 슬롯1 `06:00~11:00` |
| 2 | 점심 피크 `11:00~14:00` | 점심피크 `10:55~14:00` | 슬롯2 `11:00~13:00` |
| 3 | 점심 피크 후 `14:00~17:00` | 점심 논피크 `14:00~16:55` | 슬롯3 `13:00~17:00` |
| 4 | 저녁 피크 `17:00~20:00` | 저녁피크 `16:55~20:00` | 슬롯4 `17:00~21:00` |
| 5 | 저녁 피크 후 `20:00~23:00` | 저녁 논피크 `20:00~00:00` | 슬롯5 `21:00~23:00` |

**해석:** 슬롯은 고정 정의가 아니라 **정책별 설정값**입니다. 용어집의 시간대는
초기 기획 예시가 그대로 남은 것으로 보입니다.

**슬롯 이름도 다릅니다.** 용어집은 `점심 피크 후` / `저녁 피크 후`,
실제 운영은 `점심 논피크` / `저녁 논피크`입니다.

**액션:**
- 용어집의 슬롯 시간대 표를 "예시" 또는 "권장 기본값"으로 표기 변경
- 슬롯 명칭을 현장 용어(논피크)로 통일할지 결정

### 차이 2. "세트 물량 구성 탭"은 탭이 아니라 섹션

용어집 `세트당 기사 수` 항목 설명:

> "1세트를 수행하기 위해 필요한 최대 동시 활성 기사 수.
> 권역관리 관리정책의 **세트 물량 구성 탭**에서 설정"

실제 화면의 탭은 `기본정보` / `변경 이력` **2개뿐**이고,
`세트 물량 구성`은 기본정보 탭 안의 **6개 섹션 중 하나**입니다.

**액션:** 용어집 표기를 "기본정보 탭 > 세트 물량 구성 섹션"으로 수정

### 차이 3. 스펙아웃된 기능이 이미 운영 중이나 PRD가 없음

`00_prd_index.md` 스펙 아웃 항목:

> "3. 권역설정관리 (세트 운영 정책 + 버전 관리) | Phase 1 |
> 스펙 아웃 → 별도 PRD로 분리 (권역관리/세트분배관리)"

그런데 실제로는 **이미 구현되어 운영 중**입니다 (버전 관리까지 포함).
좌측 메뉴에 `세트분배 관리`도 함께 존재합니다.

**문제:** 분리 예정이던 별도 PRD가 `knowledge/`에 없습니다.
`zone_권역구조_개편/01_PRD.md`는 존/권역 디커플링 주제로 다른 문서이며,
이 화면을 "개편 대상 시스템"으로만 언급합니다 (1.3 적용 대상).

**액션:** 이 AS-IS 명세를 기반으로 권역정책 관리 PRD를 신규 작성할지 결정.
최소한 `00_prd_index.md`의 스펙아웃 표에 "구현 완료, PRD 미작성" 상태를 표기.

## Part 2. 화면 개선 포인트 8건

우선순위는 **운영 사고 위험도 × 발생 빈도** 기준입니다.

| # | 이슈 | 우선순위 | 성격 |
|---|------|---------|------|
| 1 | 같은 필드를 화면마다 다른 이름으로 표기 | **높음** | 용어 |
| 2 | `성공 슬롯 수 = 35`의 의미 불명확 (상한 안내 없음) | **높음** | 검증/안내 |
| 3 | 이미 연결된 ZONE이 선택 목록에서 걸러지지 않음 | **높음** | 데이터 정합성 |
| 4 | 활성/비활성 전환 경로가 화면에 없음 | **높음** | 기능 누락 |
| 5 | 슬롯 경계 시각이 겹침 (귀속 규칙 불명) | 중간 | 정책 정의 |
| 6 | 하루 24시간이 커버되지 않음 | 중간 | 정책 정의 |
| 7 | 목록 화면 정보량 부족 | 중간 | UX |
| 8 | 생성 시 슬롯2~5 기본값이 미사용 | 낮음 | 기본값 |

---

### #1. 같은 필드를 화면마다 다른 이름으로 표기 — 우선순위 높음

| 상세 화면 | 버전 비교 모달 | 용어집 |
|----------|---------------|--------|
| 성공 슬롯 수 | **최소 목표 슬롯** | (정의 없음) |
| 세트당 보상 금액 | 세트당 보상금액 (원) | 세트당 보상 (Set Reward) |
| 수락률 | 수락률 (%) | 수락률 (Acceptance Rate) |
| 세트당 최대 활성화 기사수 | 세트당 최대 활성화 기사수 | 세트당 기사 수 (Riders per Set) |

**왜 문제인가:** 운영자가 상세 화면에서 `성공 슬롯 수`에 값을 넣고,
비교 화면에서 `최소 목표 슬롯`을 보면 같은 값인지 확신할 수 없습니다.
단위도 비교 모달에서만 표기되어, 입력 화면에서는 `90`이 90%인지 90건인지 모릅니다.

**대안:**
- 용어집에 정식 명칭을 확정하고 전 화면 통일 (권장: `최소 목표 슬롯 수`)
- 입력 라벨에 단위 병기: `수락률 (%)`, `세트당 보상 금액 (원)`
- 금액에 천단위 쉼표 적용 (`300,000`)

### #2. `성공 슬롯 수 = 35`의 의미 불명확 — 우선순위 높음

성북 1 zone은 `35`로 설정되어 있는데, 이는 **7요일 × 5슬롯 = 35**로 전체 슬롯 수와 정확히 같습니다.

비교 모달의 라벨이 `최소 목표 슬롯`이므로, 이 설정은
**"주간 35개 슬롯 전부에서 목표를 달성해야 보상"** 을 의미하는 것으로 읽힙니다.

**왜 문제인가:**
- 화면에 상한값(35) 안내가 없어 운영자가 최대치를 모른 채 입력합니다
- 의도적으로 100% 달성을 요구한 것인지, 상한을 몰라 최대값을 넣은 것인지 구분 불가
- 슬롯 사용 토글을 끄면 유효 슬롯이 35개 미만이 되는데, 그때 35는 달성 불가능한 값이 됩니다

**대안:**
- 입력 필드에 `35 / 35` 형태로 분모(활성 슬롯 총 개수) 표시
- 활성 슬롯 수를 초과하는 입력에 검증 에러
- 슬롯 토글 변경 시 상한 자동 재계산

**추가 확인 필요:** 성북 정책의 35가 의도된 값인지 담당자(장석 차장 라이더팀) 확인.

### #3. 이미 연결된 ZONE이 선택 목록에서 걸러지지 않음 — 우선순위 높음

ZONE 검색 모달에서 검색어 없이 조회하면 6개 ZONE이 모두 나옵니다.
이 중 **성북 1 · 성동 1 · 동대문 1은 이미 다른 정책에 연결**되어 있는데
아무 표시 없이 선택 가능한 상태로 노출됩니다.

**왜 문제인가:** 같은 ZONE을 두 정책에 연결하면 해당 ZONE에 어느 정책이
적용되는지 모호해집니다. 배차·보상 로직에 직접 영향을 주는 설정이라
운영 사고로 이어질 수 있습니다.

**대안:**
- 이미 연결된 ZONE은 **선택 불가(disabled) + `○○정책에 연결됨` 표시**
- 정책 : ZONE 관계가 실제로 1:N이 맞는지, ZONE 입장에서 1:1이 강제되는지 확인
- 서버단 중복 연결 방어 로직 존재 여부 확인 (화면에서는 검증되지 않음)

### #4. 활성/비활성 전환 경로가 화면에 없음 — 우선순위 높음

- 목록 검색에는 `활성` / `비활성` 필터가 있음
- 상세 화면의 `상태` 필드는 **disabled** (읽기전용)
- 생성 화면에는 `상태` 필드가 아예 없음
- 목록·상세 어디에도 상태 전환 버튼이 없음

**결과:** 화면상으로는 정책을 비활성화할 방법이 없습니다.
QA 테스트 정책 6건이 정리되지 않고 운영 목록에 남아 있는 이유가
이것일 가능성이 큽니다 (정책명에 `(미사용)`, `[QA]`를 넣어 텍스트로만 구분).

**대안:**
- 상세 화면에 상태 토글 추가 (변경 시 확인 모달)
- 또는 목록에서 행별 상태 전환
- 별도 경로(DB 직접 수정 등)로 관리 중이라면 그 방법을 문서화

### #5. 슬롯 경계 시각이 겹침 — 우선순위 중간

성북 1 zone의 슬롯 경계:

```
아침         09:00 ~ 10:55
점심피크          10:55 ~ 14:00     ← 10:55 중복
점심 논피크            14:00 ~ 16:55  ← 14:00 중복
저녁피크                    16:55 ~ 20:00  ← 16:55 중복
저녁 논피크                       20:00 ~ 00:00  ← 20:00 중복
```

앞 슬롯의 종료 시각과 뒤 슬롯의 시작 시각이 동일합니다.
비교 모달에서 초 단위(`10:55:00`)까지 확인했지만 경계 귀속 규칙은 알 수 없습니다.

**왜 문제인가:** 10:55:00에 발생한 오더가 아침인지 점심피크인지에 따라
달성률 계산과 보상 판정이 달라집니다.

**대안:**
- 경계 규칙 정의 및 화면 안내 (`시작 이상 ~ 종료 미만` 등)
- 또는 종료 시각 자동 보정 (앞 슬롯 종료를 `10:54:59`로)
- 슬롯 간 겹침/공백 발생 시 화면 경고

### #6. 하루 24시간이 커버되지 않음 — 우선순위 중간

| 구분 | 커버 범위 | 미커버 |
|------|----------|--------|
| 성북 1 zone (실제) | 09:00 ~ 24:00 | **00:00 ~ 09:00** |
| 생성 화면 기본값 | 06:00 ~ 23:00 | 23:00 ~ 06:00 |

**왜 문제인가:** 미커버 시간대에 발생한 오더가 어느 슬롯에도 속하지 않습니다.
달성률 산정에서 제외되는지, 오류 처리되는지 화면으로는 알 수 없습니다.
새벽 배송이 있는 권역으로 확장할 때 문제가 됩니다.

**대안:**
- 미커버 구간 처리 정책 정의 및 문서화
- 슬롯 합계가 24시간을 덮지 않으면 화면에 경고 표시
- 커버리지를 타임라인 바로 시각화 (겹침·공백을 한눈에 확인)

### #7. 목록 화면 정보량 부족 — 우선순위 중간

현재 컬럼은 `관리정책명` / `생성일` / `마지막 수정일` 3개뿐입니다.

**왜 문제인가:**
- 검색에는 `상태` 필터가 있는데 **목록에 상태 컬럼이 없음** (필터 결과를 확인할 수 없음)
- 어느 정책이 어느 ZONE에 걸려있는지 모름
- 현재 적용 버전, 적용 시작일이 안 보임 → 예약된 변경이 있는지 목록에서 알 수 없음
- 결과적으로 9건을 하나씩 열어봐야 함

**대안:** `상태`, `적용 ZONE`, `현재 버전`, `적용 시작일` 컬럼 추가.
예약 변경이 대기 중인 정책은 배지로 강조.

### #8. 생성 시 슬롯2~5 기본값이 미사용 — 우선순위 낮음

생성 화면에서 슬롯2~5 토글이 모두 **off(미사용)** 상태로 시작합니다.
반면 실제 운영 정책 3건은 모두 전 슬롯을 사용합니다.

**왜 문제인가:** 신규 권역을 열 때마다 토글 4개를 수동으로 켜야 하고,
하나라도 빠뜨리면 해당 시간대에 물량이 배분되지 않습니다.
화면에 물량은 입력되어 있는데 슬롯이 꺼져 있으면 원인 파악도 어렵습니다.

**대안:**
- 기본값을 **사용(on)** 으로 전환
- 또는 물량이 0보다 큰 슬롯이 미사용 상태면 저장 시 경고
