# B. 버그로 보이는 것

## B-1. 판가·원가 요금제의 `적용 ZONE`이 항상 0개로 보인다

| 항목 | 내용 |
|------|------|
| **화면** | ZONE 판가 요금제 목록/조회, ZONE 원가 요금제 목록/조회 |
| **현상** | 목록의 `대상 ZONE` 컬럼이 등록된 5건 모두 `0개`. 상세의 `적용 ZONE 선택` 테이블도 행 0개 |
| **그런데** | 목록 검색 조건 ZONE에 `동대문 1`을 넣고 검색하면 `동대문1zone` 1건이 정상 반환됨 |
| **또한** | 상세 이력에 `판가 정책 Zone 추가` / `원가 정책 Zone 추가` 기록이 남아 있음 |
| **판정** | 백엔드에는 매핑이 존재하고 **조회 API 또는 화면 렌더링만 누락**된 것으로 보임 |
| **영향** | 운영자가 매핑이 안 된 줄 알고 `+ ZONE 추가`를 다시 눌러 중복 등록을 시도할 수 있음 |
| **근거 스크린샷** | `07_판가_목록.png`, `09_판가_조회.png`, `13_원가_목록.png`, `14_원가_조회.png` |

> 같은 구조인 할증·프로모션은 `대상 ZONE` / `대상 상점`이 정상적으로 `1개` 등으로 표시됩니다.
> 즉 판가·원가 두 메뉴에 국한된 문제로 보입니다.

## B-2. 운영 중인 할증 데이터가 현재 검증 규칙을 통과하지 못한다

| 항목 | 내용 |
|------|------|
| **화면** | ZONE 할증 조회 — `동대문 1_주말전체` (`/zone/extra-fees/25`) |
| **현상** | 조회하는 즉시 섹션 제목 옆에 빨간 배지 `요일 및 시간대 설정에 올바르지 않은 범위가 포함돼있습니다.` |
| **상세** | 월: `00:00 ~ 03:00` → `✗ 첫 번째 종료 시간이 잘못됐습니다` / 일: `06:00~23:59` + `00:00~03:00` → `✗ 두 시간대가 겹칩니다` |
| **추정 의도** | "주말(토·일) 06:00 ~ 익일 03:00" 할증. 타임라인이 29:59까지 지원하므로 `24:00~27:00`으로 입력해야 함 |
| **실제 입력** | 익일 구간을 `00:00~03:00`으로 입력 → 같은 날 새벽으로 해석되어 규칙 위반 |
| **영향 1** | 이 할증이 실제로 심야에 적용되는지 불확실 (백엔드 해석 방식 확인 필요) |
| **영향 2** | 금액만 수정하려 해도 검증에 걸려 저장이 막힐 가능성 |
| **근거 스크린샷** | `17_할증_조회_요일시간대_상단.png`, `18_할증_조회_요일시간대_하단.png` |

> 이 데이터는 2026-06-10부터 무기한(`종료일 -`)으로 적용 중인 **유일한 실운영 할증**입니다.

## B-3. 안내문구가 다른 화면에서 복사·붙여넣기 된 상태로 남아 있다

| 화면 | 실제 문구 | 문제 |
|------|----------|------|
| ZONE 할증 > 적용 ZONE 선택 | `» ZONE별로 1개의 **원가 요금제**만 적용 가능합니다. 요금제는 복수의 ZONE에 적용할 수 있습니다.` | 할증 화면인데 "원가 요금제". 게다가 할증은 ZONE당 여러 건 존재(실데이터로 확인) → **내용도 사실과 다름** |
| G4 프로모션 > 적용 ZONE 선택 | `» ZONE별로 1개의 **판가 요금제**만 적용 가능합니다. 요금제는 복수의 ZONE에 적용할 수 있습니다.` | 프로모션 화면인데 "판가 요금제" |

**영향:** 운영자가 "할증도 ZONE당 1개만 되는구나"라고 잘못 이해합니다.
실제로는 동대문 1에 할증이 5건 등록되어 있었습니다.

**수정 방향:** 할증·프로모션의 실제 제약(ZONE당 N개 허용)에 맞는 문구로 교체.

## B-4. 추가(신규 생성) 화면에 `삭제` 버튼이 있다

| 화면 | 하단 좌측 버튼 |

> 판가·원가 추가 화면에는 삭제 버튼이 없습니다(`목록으로`/`저장`만). 4개 메뉴 간에도 일관되지 않습니다.

## B-9. 개발 enum(`ACTIVE`/`INACTIVE`)이 화면에 그대로 노출된다

| 화면 | 노출 지점 | 문구 |
|------|----------|------|
| 벤더 조회 > 벤더장(VO) 섹션 | 안내문구 | `» 운영중(ACTIVE) 상태에서는 VO 해제 불가. 교체만 가능합니다. 해제하려면 먼저 **INACTIVE**로 변경하세요.` |
| 벤더 조회 > 소속기사 탭 | 테이블 `소속 상태` 컬럼 | `ACTIVE` (11명 전원) |

**가장 큰 문제:** `INACTIVE`라는 상태가 화면 어디에도 표시되지 않습니다.
목록·상세의 상태값은 `운영중` / `운영중지` / `대기` / `해지`이고, 하단 버튼은 `운영 중지` / `해지`입니다.
운영자는 안내문구를 읽어도 **무엇을 눌러야 하는지 알 수 없습니다.**

**수정 방향:** `INACTIVE` → `운영중지`로 치환하고, `운영 중지` 버튼을 누르라고 명시.

# I. 개선하면 좋은 것

## I-1. ZONE 하나를 오픈하려면 사이드바 3곳을 왕복해야 한다

신규 ZONE 오픈에 필요한 작업 순서 (추정):

```
1. 영업 관리 > ZONE 관리          → ZONE 생성 (지점 매핑)
2. 세트 관리 > ZONE 권역정책 관리  → 슬롯·단위물량 설정
3. 세트 관리 > 벤더 관리           → 벤더 등록
4. ??? (경로 불명, Q-7)            → 벤더 ↔ ZONE 연결
5. 세트 관리 > 세트분배 관리       → 벤더별 세트 수 배분
6. G4 요금 상품 관리 > 판가 요금제  → 판가 설정 + ZONE 매핑
7. G4 요금 상품 관리 > 원가 요금제  → 원가 설정 + ZONE 매핑
8. G4 요금 상품 관리 > ZONE 할증    → (필요 시) 할증 설정
```

**문제:**
- 8단계가 사이드바 3개 그룹에 흩어져 있고 **순서를 알려주는 화면이 없음**
- 완료 여부를 확인할 통합 화면도 없음 → 실제로 성북·성동은 6·7번이 누락된 상태 (Q-1)
- 신규 담당자가 인수인계 없이 수행하는 것은 사실상 불가능

**개선안:**

| 안 | 내용 | 난이도 |
|----|------|:------:|
| A (즉시) | ZONE 오픈 체크리스트 문서화 → `knowledge/`에 SOP로 남김 | 낮음 |
| B (단기) | ZONE 관리 상세에 "설정 완성도" 패널 추가 (판가·원가·권역정책·세트분배 연결 여부 ○/✗) | 중간 |
| C (중기) | ZONE 오픈 위저드 화면 (단계별 진행, 미완료 항목 표시) | 높음 |

> B안만 있어도 Q-1(성북·성동 요금제 누락)을 화면에서 즉시 발견할 수 있었습니다.

## I-2. 지점 드롭다운이 이미 ZONE에 매핑된 지점을 걸러내지 않는다

| 항목 | 내용 |

## Q-2. 원가 거리별 단가가 판가의 2.3배인 것은 의도인가

동대문 1 요금 구조:

| 구분 | 기본 | 거리 구간 1 | 거리 구간 2 | 거리별 최고가 | VAT 포함 최대 |
|------|------|------------|------------|--------------|--------------|
| 판가 | 4,300원 | 0~1㎞ 정액 0원 | 1~10㎞ **0.1㎞당 100원** | 9,000원 | 14,630원 |
| 원가 | 라이더비 4,200원 | 0~1.5㎞ 정액 0원 | 1.5~10㎞ **0.1㎞당 230원** | 19,550원 | 26,125원 |

**확인할 것:**
1. 거리별 단가 230원(원가) vs 100원(판가)이 의도된 설정인가
2. 장거리 오더에서 원가 > 판가가 되는데, 할증·프로모션을 얹으면 마진이 확보되는 구조인가
3. 구간 경계가 판가 1㎞ / 원가 1.5㎞로 다른 이유는 무엇인가 (1~1.5㎞에서 판가만 거리요금 발생)

> 판가에는 할증이 별도로 얹히고, 실제 오더의 거리 분포도 봐야 하므로 **단정할 수 없습니다.**
> 다만 화면상으로는 역마진 구간이 존재하므로 설계 의도 확인이 필요합니다.
> 참고 문서: `knowledge/1_discovery/data_analysis/20260608_벤더4563_매출원가_검증_및_마진분석.md`

## Q-3. 원가 요약 합계식에서 관제비·관리비가 빠진 것은 의도인가

| **벤더 등록 화면** | 소속 Zone 섹션이 **아예 없음** |
| **세트분배 조회 > 벤더 구성** | 벤더를 추가할 수 있지만, 이것이 "소속 Zone"을 설정하는 것과 같은 동작인지 불명 |
| **변경 이력** | `존 연결 — {UUID}` 기록이 존재 (백호: 2026-07-21 18:28, 김가연 라이더팀) |

**시각 대조 (성북 1):**

| 시각 | 벤더 이력 | 세트분배 이력 |
|------|----------|--------------|
| 7/21 15:22 | 벤더 신규 등록 / 벤더장 지정 / 상태 변경 (장석) | v2 예약 생성 (장석, 7/22 06:00 적용 예정) |
| 7/21 18:28 | **존 연결 — 4b755c79…** (김가연) | **v1 생성 = 현재 적용** (김가연) |

시각이 정확히 일치합니다. **세트분배 화면에서 벤더를 추가·저장하면 그것이 `존 연결`로 기록되는 것으로 추정**됩니다.

**확인할 것:**
1. 위 추정이 맞는가 (세트분배 저장 = 벤더-ZONE 연결)
2. 맞다면 벤더 조회의 `소속 Zone` 섹션은 세트분배 결과를 보여주는 것인가
3. 벤더를 다른 ZONE으로 옮기려면 어떻게 하나 (세트분배에서 삭제 후 다른 ZONE에 추가?)
4. 왜 v2(예약)가 취소되고 v1이 만들어졌나 — 예약 저장 방식으로는 존 연결이 안 되기 때문인가

> 이것이 확정되지 않으면 **ZONE 오픈 SOP를 쓸 수 없습니다.** (I-1 A안의 전제 조건)

## Q-8. 벤더 상태 전이 규칙은 무엇인가

| 항목 | 내용 |

| **상세 화면의 전이 버튼** | `운영 중지` / `해지` — 2개뿐 |
| **이력에 남은 전이** | `상태 변경 — 대기 → 활성 · 사유: 성북 신규 라이브 (7/22)` |

1. `대기 → 운영중` 전이는 어디서 하나 (대기 상태일 때만 `운영 시작` 버튼이 나타나는가?)

3. `해지` 후 되돌릴 수 있는가 (드림푸드 사례를 보면 불가능해 보임)
4. 상태 전이 시 `사유` 입력은 필수인가 (이력에 사유가 기록되어 있음)

## Q-10. 할증·프로모션의 `활성화 상태`(예정/진행중/종료)는 어떻게 결정되나

| 항목 | 내용 |
|------|------|
| **목록 검색 조건** | 체크박스 4개 `전체` `예정` `진행중` `종료` (기본: 전부 체크) |
| **상세 화면** | 상태를 직접 지정하는 필드가 **없음** |
| **추정** | 시작일·종료일과 현재 시각을 비교해 파생 |

**확인할 것:**
1. 위 추정이 맞는가 (파생값인가, 별도 저장 필드인가)
2. `전체` 체크박스는 상위 토글인가, `예정/진행중/종료`와 병렬인 별도 값인가
3. 4개를 모두 해제하면 어떻게 되나 (전체 조회? 0건?)
4. `적용 시간`(00:00~23:59)이 상태 판정에 반영되나 — 예: 시간대 밖이면 `진행중`이 아닌가

## Q-11. 할증 시간대의 `24:00~29:59` 표기는 백엔드에서 어떻게 해석되나

| 항목 | 내용 |
|------|------|
| **화면** | 요일 및 시간대 할증의 타임라인 우측 끝 라벨이 `29:59` |
| **의미 추정** | 자정 넘김 구간을 익일 시각으로 표현 (24:00 = 익일 00:00, 29:59 = 익일 05:59) |
| **문제** | 운영 데이터(`동대문 1_주말전체`)는 익일 구간을 `00:00~03:00`으로 입력해 검증 오류 (B-2) |

**확인할 것:**
1. `24:00~27:00`과 `00:00~03:00`은 백엔드에서 다르게 처리되는가
2. 다르다면 현재 동대문 1 심야 할증은 **적용되지 않고 있는 것인가**
3. `일요일 00:00~03:00`은 "일요일 새벽"인가 "월요일 새벽"인가
4. 최대값이 29:59인 이유 (익일 06:00 이전까지만 허용하는 정책적 이유가 있는가)

> Q-11의 답에 따라 B-2가 **단순 UI 검증 문제**인지 **실제 할증 미적용 사고**인지가 갈립니다.

## Q-12. 세트분배의 `예약 저장`과 버전 관리는 어떻게 동작하나

| 항목 | 내용 |
|------|------|
| **버튼** | 세트분배 조회 하단 `예약 저장` (`저장`과 별도) |
| **성북 1 이력** | v2(취소됨, 7/22 06:00 적용 예정) / v1(현재 적용, 7/21 18:28) |
| **이상한 점** | 버전 번호가 큰 v2가 취소되고 작은 v1이 현재 적용 |

**확인할 것:**
1. `저장`과 `예약 저장`의 차이 (즉시 적용 vs 시점 지정)
2. 예약 중에 `저장`을 하면 예약이 자동 취소되는가 (성북 1 사례가 이것으로 보임)
3. 버전 번호는 생성 순서인가, 적용 순서인가
4. `상태` 컬럼의 가능한 값 전체 (`현재 적용` / `취소됨` 외에 `예약`, `과거 적용` 등이 있는가)
5. 버전 비교 모달의 `변경` 컬럼 값 전체 (`동일` 외에 무엇이 있는가)
6. 예약을 수동으로 취소하는 방법이 있는가

> `ZONE 권역정책 관리`도 동일한 예약 저장·버전 비교 구조를 가지므로,
> 답을 받으면 두 문서에 함께 반영합니다.
