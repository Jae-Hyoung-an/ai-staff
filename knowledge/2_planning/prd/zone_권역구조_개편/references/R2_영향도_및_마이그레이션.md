## 0. 요약 — 이 개편의 실제 난이도는 어디에 있나

개발 1-Pager의 표현을 그대로 옮기면 이렇다.

> "지금은 생성 때 한 번 계산하면 끝나던 원가가, **'누가 수행하느냐'라는 배정 시점 정보**를 필요로 하게 됐다. 구현 난이도 대부분이 여기서 나온다."

화면 신설(원가 요금제 탭, 원가 할증 메뉴, 시각화)은 비용이 예측 가능하다. 실제 리스크는 아래 세 곳이다.

| # | 리스크 | 왜 |
|---|--------|---|
| **R1** | **정산 집계 축 변경** | vendorset 정산 레코드의 존 축이 "주문의 존"(`offerOrder.zoneUuid`)이다. 원가를 수행 벤더 기준으로 바꾸는 것은 정확히 이 축을 바꾸는 일이고, 잘못되면 벤더 지급액이 틀린다 |
| **R2** | **배정 전 `agentFee`를 읽는 경로 전수 확인** | 원가는 오더 생성 때 계산·저장되고 완료 때 그 값이 이체된다. 배정 시점 확정으로 바꾸려면 그 사이에 `agentFee`를 읽는 모든 경로를 찾아야 한다 |
| **R3** | **정책 문서 3층 불일치** | 정책서 v3.0 / Zone 요금제 Phase2(QA 중) / 프로덕션 인트라가 서로 다른 상태다. 어느 것을 기준으로 개발할지 합의하지 않으면 산출물이 뒤집힌다 |

## 1. 시스템별 영향도

### 1.1 권역 서버 (region)

| 항목 | 내용 |
|------|------|
| **유리한 점** | 좌표→권역 판정 인프라(공간쿼리 + JTS) 보유. **권역 중첩을 막는 검증이 없어** 중첩 허용과 충돌하지 않는다. 전용 권역 도메인을 분리한 선례(`PricingPolicyRegion`)도 있다 |
| 신규 | 벤더 배송권역 도메인 (중첩 허용) |
| 신규 | 좌표 → 벤더 배송권역 판정 API (출·도착지, 복수 권역 반환) |
| 신규 | 픽업지 권역 **연결 상태 조회 API** (어느 영업존에 연결됐는지 — 중복 선택 차단용) |
| 신규 | 픽업지 권역 **지리 중첩 감지 API** (다른 지점 권역과의 중첩 경고용, 차단 아님) |
| 신규 | 지점 픽업지 권역 변경 시 사후 중첩 감지 훅 |
| 변경 | 상점 판매권역(`STORE_SALES_REGION`) 생성 소스: 관제지점 공급권역 → 영업존 픽업지 권역 + 배송 반경 (**G4 한정**) |
| 변경 | 지점 공급권역 ↔ 벤더 배송권역 **상시 동기화**. 배송권역은 공급권역 참조만 보유하며 자체 지오메트리를 갖지 않는다 |
| 신규 | 공급권역 변경 시 **참조 중인 배송권역 정책 알림 + 이력 적재** 훅 (E-17) |
| 신규 | 공급권역 삭제 시도 시 **참조 정책 존재 여부 검사** (참조가 있으면 차단) |
| **삭제** | 권역 편집기(폴리곤 직접 작성·수정) 개발 범위 — 직접 그리기 폐기로 불필요 |

### 1.2 요금제 서버 (pricing-policy)

| 항목 | 내용 |
|------|------|
| 변경 | 원가 요금제 소유 축: ZONE → **배송권역 정책** |
| 변경 | 원가 스키마: 고정비 4항목(단일값) + 라이더비(요일 × 슬롯 매트릭스) + 거리 할증(**다구간 구간표**, 판가 구조 재사용) |
| 변경 | 판가 요금제의 영업존 **직접 매핑** (통합 요금제 경유 제거) |
| 변경 | 할증 분리: 판가 할증(영업존) / 원가 할증(배송권역 정책) |
| 신규 | 권역 외 할증 타입 |
| 신규 | 원가표 제공 API (오더 1건에 대한 후보 권역별 원가 목록) — 원가표 생성 주체가 요금제 서버로 결정되는 경우 |
| ⚠ 주의 | `pricingPolicyUuid`가 정산·스트림 어디로도 전파되지 않는다. "선택된 요금표"를 정산까지 남기려면 **전부 신규 배관**이다 (TBD-7) |

### 1.3 라스트마일 (lastmile)

| 항목 | 내용 |
|------|------|
| 신규 | 오더 분류값(권역 내/외/회귀) 계산·보유 |
| 신규 | 후보군 응답에 후보별 분류·원가 적재 |
| **변경** | **원가 확정 시점: 생성 → 배정.** 배정 전 `agentFee`를 읽는 모든 경로 전수 확인 (R2) |
| 변경 | 배정 요청에 `vendorId` 추가 (현재 `agentTotalFee`·`dispatchSource`만 전달) |
| 변경 | 재배차 시 원가 재확정 |
| ⚠ 선례 | AI배차 배정 요청의 제안 금액과 기존 스냅샷 차액을 `AI_ADJ` 할증으로 얹는 로직(`applyAiAdjustmentExtraCharge`)이 이미 있다. "기존 원가 유지 + 배정 시점 조정"이 부분 구현돼 있어 **출발점으로 쓸 수 있다.** 단 이중 가산 방지 필요(E-13) |
| ⚠ 주의 | 완료 시 재계산되는 요금은 `monitoringFee` 하나뿐이다(프렌즈 G1이면 0, 과적은 제외). 완료 시점 재검증을 얹으려면 이 선례와의 충돌을 봐야 한다 |
| ⚠ 주의 | 정산 경로가 `dispatch_source == SET` 기준으로 갈린다(벤더 = 이력 적재·원천세 미차감 / 그 외 = M캐시 이체+원천세). 배차포기 수수료만 "포기한 기사의 멤버십" 기준 → E-15 |

### 1.4 배차 (dispatch)

| 항목 | 내용 |
|------|------|
| ⚠ 구조 | 벤더 오더의 기사 후보는 라스트마일이 아니라 **vendorset이 존 단위로 공급**한다 (`AgentClientRouter` → `/api/v2/zones/{zoneUuid}/dispatch-candidates`, 일반 오더는 lastmile 후보군 API, 이후 머지) |
| 변경 | 위 라우팅의 축을 권역 기준으로 재정의 — **TBD-2**. "후보별 분류·원가를 누가 실어주나"가 이 구조 위에서 결정된다 |
| 변경 | 분류·원가 정렬키 반영 (하드 필터 + 3단 정렬) |
| 신규 | 회귀 오더 제안 (기사 위치 게이트) |
| ⚠ 주의 | 자기 벤더(관할) 오더는 도착지와 무관하게 노출·제안된다. 노출 쿼리에 도착지 조건이 없고(`findSubmittedOrderByPartnerId`) 추천배차 거리 필터도 자기 지점 라이더는 면제다. **3분류를 도입하면 이 무조건 노출과 정합을 맞춰야 한다** |
| ⚠ 주의 | 라스트마일 후보군 조회는 기사 위치를 보지 않는다. 벤더 오더 후보의 위치는 vendorset 응답에 실려온다 → 회귀 오더의 기사 위치 소스 결정 필요 |

### 1.5 벤더 관리 (vendorset)

| 항목 | 내용 |
|------|------|
| ⚠ 소유 | 기사→벤더 매핑 원본은 `vendor_agents`. 라스트마일은 push받는 `vendorId`를 로깅만 하고 버리며, **풀싱크 payload에는 vendorId가 없다**(upsert/inactivate에만 있음 — 비대칭 주의) |
| ⚠ 소유 | 벤더→존 매핑도 vendorset(`Vendor.zone_uuid`, 벤더:존 = N:1). 인트라 `ZONE 권역정책 관리`의 백엔드도 vendorset이다 |
| **변경** | **정산 집계 축: "주문의 존" → 수행 벤더의 배송권역 정책** (R1, TBD-1) |
| 변경 | `ZonePricingFetcher.fetch(zoneUuid)` → 배송권역 정책 기준 조회 |
| 변경 | 벤더:배송권역 정책 카디널리티 — TBD-3 |
| 변경 | 세트분배 기준 축: 존 → 배송권역 정책 |
| ⚠ 확인 | **벤더-존 연결을 만드는 화면 경로가 AS-IS에 없다.** 벤더 상세 `소속 Zone`은 읽기 전용, 등록 화면에는 섹션 자체가 없는데 변경 이력에는 `존 연결` 기록이 남는다. 경로를 찾아야 배송권역 정책 연결로 전환할 수 있다 |

### 1.6 delivery

| 항목 | 내용 |
|------|------|
| ⚠ 구조 | delivery는 원가를 계산하지 않고 라스트마일이 확정한 금액을 받아 3곳에 저장한다(`DeliveryFeeUpdater`, set 방식). **배차완료 직후 라스트마일에서 오더 상세(fee)를 조회**해 간다 |
| 변경 | 원가 확정 시점이 바뀌면 이 조회 타이밍·값 정합성 보정 필요. 배정 후 fee 갱신 선례(기사 개인할증 이벤트)가 이미 있다 |
| ⚠ 주의 | 라스트마일 이벤트 소비는 기본 NVP 오더만이지만 **취소·개인정보 파기·과적 완료는 nvpOrder=false도 처리**한다. 오더에 새 필드(분류 등)를 실으면 이 경로도 지나간다 |

## 2. 데이터 마이그레이션

### 2.1 현행 데이터 규모 (2026-07-29 운영 기준)

| 대상 | 건수 | 실운영 |
|------|------|--------|
| ZONE | 6건 | 3건 (성북 1 / 성동 1 / 동대문 1) |
| 판가 요금제 | 5건 | 3건 활성 |
| 원가 요금제 | 5건 | 3건 활성 |
| ZONE 할증 | 7건 | 동대문 1건(`동대문 1_주말전체`) + QA |
| G4 프로모션 | 5건 | **0건** (전부 QA) |
| ZONE 권역정책 | 9건 | 성북 1 zone 등 |
| 벤더 | 26건 | 8건 (나머지는 QA·해지 잔여물) |
| 세트분배 | 6건 | ZONE 수와 동일 |
| 지역 폴리곤 | 1건 | 0건 (QA만) |

> **규모가 작다.** 실운영 존 3개, 실운영 할증 1건이다. 마이그레이션 난이도 자체는 낮고, 리스크는 "전환 중 원가 공백"에 집중된다.

### 2.2 마이그레이션 순서

| 단계 | 작업 | 검증 |
|------|------|------|
| **M1** | 영업존 = 기존 ZONE 승계. 픽업지 권역은 **동일 이름의 대표 권역 1개**를 연결(예: `성북 1 zone`). 남는 채널 픽업지(`YOGIYO_OD` 등)는 **미연결 상태로 남긴다** | 존 3건의 대표 픽업지 권역 선정 확인. 미연결 픽업지 목록 리포트 |
| **M1-a** | 미연결 채널 픽업지에 대한 처리 방침 결정 — 별도 영업존 생성 vs 미연결 유지 | ⚠ 미연결 상태의 상점에 판가가 붙지 않으므로 **전환 전 반드시 확인**. 현재 채널 픽업지에 실제 상점이 있는지 조회 필요 |
| **M2** | 픽업지 권역 참조 중복 검사 실행 | 1:1 구조이므로 중복 0건 예상 |
| **M3** | 판가 요금제의 존 매핑을 통합 요금제 경유 → 직접 매핑으로 전환 | 존별 판가 요금제 1:1 확인. AS-IS의 "대상 ZONE 0개 표시" 결함 때문에 **백엔드 매핑을 직접 조회해 검증** |
| **M4** | 배송권역 정책 = 기존 ZONE 권역정책 그대로 승계. 배송권역은 기존 연결 ZONE의 **지점 공급권역 참조**로 생성 (상시 연동) | 정책 9건의 배송권역 생성 확인. 동일 공급권역 중복 참조 0건 |
| **M5** | 원가 요금제 이관: 기존 ZONE 원가 요금제 → 배송권역 정책의 원가 요금제 | ① 고정비 4항목 그대로 복사 ② 라이더비는 기존 기본원가를 **전 슬롯·전 요일에 동일 값으로 채움** ③ 거리 할증은 기존 **다구간을 구간 그대로 이관** (무손실) |
| **M5-a** | AS-IS `ZONE 원가 요금제 관리` 메뉴(`/zone/cost-pricings`) 제거 | 이관 완료 5건 검증 후 제거. 정산이 이 경로를 직접 조회하지 않는지 확인 |
| **M6** | 할증 분리: 원가 금액이 있는 할증을 원가 할증으로 복제 생성 → 판가 할증에서 원가 필드 제거 | **복제 후 제거 순서 필수.** 반대로 하면 원가 공백 발생 |
| **M7** | 요일·시간대 할증로 우회 구현했던 원가 차등을 라이더비 매트릭스로 이전 → 우회 할증 종료 | 동대문 `동대문 1_주말전체`(원가 200원, 토·일 06:00~) → 해당 요일·슬롯 라이더비에 가산 후 할증 종료 |
| **M8** | 세트분배 기준 축을 존 UUID → 정책 UUID로 전환 | 6건 확인 |
| **M9** | 상점 판매권역 재생성 (관제지점 공급권역 → 영업존 픽업지 권역 + 배송 반경). **G4 상점만** | 기존 반경과 동일 결과인지 **상점 표본 비교**. 차이가 나는 상점 목록 리포트. G1~G3 상점의 판매권역이 변하지 않았는지 확인 |
| **M10** | 상점 운영정보 ZONE 필드를 자동 판정으로 전환, 불일치 건은 수동 오버라이드로 보존 | 불일치 상점 목록 확인 |

### 2.3 M5 상세 — 원가 구간 이관 (무손실)

동대문 1zone 실데이터 예시:

| AS-IS 구간 | 요금제 | 단위거리 | 요금 |
|-----------|--------|---------|------|
| 0 이상 ~ 1.5 미만 | 정액제 | 0 | 0원 |
| 1.5 이상 ~ 10 미만 | 거리별 | 0.1 | 230원 |

| TO-BE 항목 | 값 | 근거 |
|-----------|---|------|
| 기본 거리 | 1.5 km | 첫 정액 구간의 끝 |
| 라이더비 (전 슬롯·전 요일) | 4,200원 | 기존 라이더비(기본원가) |
| 거리 할증 구간 1 | `1.5 ~ 10 km` / 단위 0.1 km / 230원 | 두 번째 구간 그대로 |

**변환 규칙**

| AS-IS | TO-BE |
|-------|-------|
| 첫 번째 정액 구간(0 ~ N) | `기본 거리 = N`으로 흡수. 이 구간의 원가는 라이더비 매트릭스가 담당 |
| 두 번째 이후 거리별 구간 | 거리 할증 구간 테이블에 **순서대로 1:1 이관** |
| 마지막 구간의 끝 | 그대로 마지막 구간의 끝 = 최대 상한 거리 |

거리 할증이 다구간 테이블이 되면서 **3구간 이상 데이터도 손실 없이 이관**된다. 판가와 동일한 구조이므로 변환 로직도 판가 쪽을 재사용할 수 있다.

### 2.4 M6 상세 — 할증 분리 순서

```
[1] 원가 금액이 있는 할증을 식별 (동대문 5건 등)
     ↓
[2] `원가 할증 관리` 메뉴에 동일 조건으로 복제 생성 → 해당 배송권역 정책에 적용
     - 할증명, 종류, 적용일자/시간, 요일·시간대 설정, 원가 금액
     ↓
[3] 복제 결과 검증 (원가 합계가 기존과 동일한지 오더 시뮬레이션)
     ↓
[4] 판가 할증에서 원가 필드 제거 (스키마 변경)
     ↓
[5] 판가 0원인 할증은 판가 할증에서 종료 처리
```

⚠ 동대문 할증 5건은 **전부 판가 0원 / 원가만 부여**다. 즉 [5]에서 판가 할증 쪽에는 남길 것이 없다. 순서를 뒤집으면 원가가 통째로 사라진다.

## 3. 롤아웃 계획 (제안)

| 단계 | 내용 | 검증 |
|------|------|------|
| **P0. 선행 협의** | Phase2 롤백 범위 / 정책서 v3.0 개정 / ITSMCHG-33545 머지 여부 | 합의 문서화 |
| **P1. 읽기 전용 병행** | 새 구조(영업존·배송권역 정책·원가 요금제)를 만들되 **배차·정산은 기존 로직 유지**. 신구 원가를 병렬 계산해 로그만 적재 | 신구 원가 차이 리포트 — 차이가 예상 범위인지 |
| **P2. 1개 존 파일럿** | 성북 또는 동대문 1개 존에서 새 원가·분류·배차 적용 | 벤더 정산 대조, 배차 성공률, CM |
| **P3. 전체 전환** | 실운영 3개 존 전환 | 가드레일 지표 감시 |
| **P4. G1 원가 일원화** | 별도 릴리스로 분리 | 재무 영향도 재확인 |

> **P1(신구 병렬 계산)을 반드시 넣을 것을 권한다.** 원가 확정 시점 변경은 정산 금액에 직결되고, 사후 발견되면 벤더 지급 정정이 필요해진다. 병렬 로그만으로도 대부분의 오류를 사전에 잡을 수 있다.
