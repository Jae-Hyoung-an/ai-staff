# 배경 — 위탁지점 체계의 한계와 벤더 구조로의 전환

> 벤더관리 시스템이 "왜" 필요한지에 대한 전략적 배경.
> AS-IS(기존 위탁지점)의 구조적 문제와 TO-BE(벤더 구조)의 해결 방식을 정리.
> 정책/기능의 근거(Why)로, `00_prd_index.md`·`02_정책서.md`와 함께 참조.

---

## 한 줄 요약

> 지점에 **전부 위임**하던 구조를 → 본사가 **물량(영업)·배차(AI)·공급예측을 통제**하고,
> 벤더는 **발주받은 물량만 거절 없이 기사를 확보해 수행**하는 구조로 전환한다.

---

## 전환 전략 (Scope & Rollout)

| 항목 | 내용 |
|------|------|
| **궁극 목표** | **전 지역**의 배송 인프라를 벤더 구조로 전환 |
| **방식** | 레거시(위탁지점) 구조를 한 번에 바꿀 수 없으므로 **순차적 전환** |
| **첫 테스트** | **동대문구** — 기존 위탁 인프라를 제거하고 벤더 구조로 전환 중 |

> ⚠️ KB(`00_prd_index.md`)는 이 시스템을 "B존(라이더 인프라 취약 지역) 대상 NVP-B 전략"으로 서술하지만,
> 실제 지향점은 **B존에 한정되지 않은 전 지역 전환**이며, B존/동대문구는 그 **첫 적용 단계**다.

## AS-IS: 기존 위탁지점 체계의 7대 문제

| # | 문제 | 핵심 원인 |
|---|------|----------|
| 1 | **SLA 준수 동인 부족** | 완료 **건당 관리관제fee** 수익 구조 → 적시 배송 인센티브 없음 |
| 2 | **본사 법인물량 후순위** | 지점이 **로컬물량**(이전 가능한 본인 수익원)을 우선 처리 |
| 3 | **'꿀콜'만 선택, 나머지 방치** | **전투배차**(기사 자율 선택) → 저수익 오더 유기 → 고객만족 저하 |
| 4 | **전체 최적 배차 미실현** | 경쟁적 선택 → 동일 기사 수로 더 많이 처리하는 최적 배분/경로 불가 |
| 5 | **문제 지점 교체 곤란** | **1지역 1지점 독점** 인정 |
| 6 | **필요 기사 공급 안 됨** | 개인사업자가 기사 모집·관리 → 퀄리티보다 기사 수익보전 우선 |
| 7 | **물량 증대·컨트롤 불가** | 상점 영업까지 지점에 위임 |

## TO-BE: 벤더관리 시스템의 해결 방식

| # | 해결책 | 대응 문제 |
|---|--------|----------|
| 1 | **AI 배차 제안 시스템**을 기본으로 사용 → 최적 배차 실현 | #3, #4 |
| 2 | **본사가 직접 권역 설계** (최적 운영 전제) | #4, #5 |
| 3 | 권역별 예측 물량을 요일·시간 단위 **'세트'**로 쪼개 **다수 벤더에 발주** | #5, #7 |
| 4 | 벤더 **오더 수행 실적을 주간 평가 → 보상 차등** (수요 대비 공급 컨트롤러빌리티 확보) | #1, #6 |
| 5 | 소단위 분배 → 정책 미충족 벤더를 **부담 없이 빠르게 교체** | #5, #6 |

**실적 평가 기준 (예시)**
- 발주 물량을 전부 **적시에 처리**했는가
- 본사가 시도한 배차를 **낮은 거절률로 모두 수락**했는가

## 궁극 구조 (Target Operating Model)

| 주체 | 역할 |
|------|------|
| **본사** | 물량 공급(영업) · 최적 배차(AI 배차) · 공급(기사) 예측을 **전부 통제** |
| **벤더** | 발주받은 물량을 **거절 없이** 수행 + 필요한 **기사 확보**만 담당 |

## 핵심 개념 정의 (확정)

| 용어 | 정의 |
|------|------|
| **AI 배차 제안 시스템** | 이번에 구축한 **Dispatch Service**(통합 배차 엔진). 가중치 기반으로 적합 기사 선정 |
| **법인물량** | 본사가 **B2B로 체결한 전국 대단위 물량 계약** |
| **로컬물량** | 본사가 아닌, **상점 단위로 직접 계약**한 상점들의 물량 (지점이 타 플랫폼 이전 시 함께 이동 가능) |
| **관리관제fee** | 기존 위탁지점의 보상. 배달 **건별 완료 시점에 실시간으로 위탁지점에 직접 지급** (벤더관리 시스템의 주간 일괄 정산과 대비됨) |
| **거절 통제 방식** | 시스템이 거절을 **물리적으로 막지 않음**. 거절은 가능하되 **벤더 단위 실적·보상으로 통제** |

## 체계 구축에 필요한 준비

새 체계를 만들기 위해 **(1) 시스템 개발**과 **(2) 운영 SOP** 양 축의 준비가 필요했다.

| 축 | 내용 |
|----|------|
| **시스템 개발** | **MVP 스펙**으로 우선 개발 진행 |
| **운영 SOP** | 처음 시도하는 운영 방식 → 신규 SOP 다수 준비 필요 (아래) |

### SOP 준비 현황 *(2026-06 기준)*

**동대문구**를 첫 테스트 지역으로 선정해 새 벤더 구조를 도입. 그 과정에서:

| SOP | 상태 |
|-----|------|
| (1) 초기 진입 권역설계 | **상세하게 수립 완료** (진입에 직접 필요) |
| (2) S&OP | **아웃라인만** 잡힘, 상세화 미완 |
| (3) 상점 CX | **아웃라인만** 잡힘, 상세화 미완 |

### 운영 SOP — (1) 초기 진입 전 권역설계 *(지역 진입 시 1회성)*

- 최적 배차를 위한 **권역 설계**
- **영업 조건** 준비 (상점 영업용): 배송 범위, 가격, 할증, 운영시간 등
- **수행 조건** 준비 (벤더가 매력을 느낄 조건): 기사 배송 원가, 벤더 인센티브(주간 평가로 지급하는 금액), 세트 물량 설계, 거절률 기준 설계
- **영업 조건 ↔ 수행 조건** 간 수익성 분석 + 경쟁사 대비 비교 → **최종안** 도출

> 권역은 진입 후에도 **필요하면 조정 가능**. 다만 진입 후 조정은 아래 S&OP 흐름 안에서 다룬다.

### 운영 SOP — (2) S&OP *(주간 반복)*

> **목적**: 총 물량(=매출)과 서비스 레벨을 높이기 위해 **현황 파악과 조치를 반복**하는 프로세스.

본사가 통제권을 갖고 배송 퀄리티를 개선하려면 **수요(물량)·공급(기사) 예측**이 핵심.

- **수요 예측**: 과거 트렌드 + 현재 상점 영업 진행 상황(법인·로컬 모두) + 물량 영향 이벤트(중요 경기 등) → 차주 **요일·시간대별 물량** 예측
- **공급 필요량 산정**: 배송 퀄리티 ↔ 기사별 수익의 밸런스를 고려한 **기사 공급 필요량** 파악
- **발주/계약 계획**: 차주 벤더별 **발주 세트 수**, 벤더 **추가 계약/해지** 계획
- **공급 pool 구성**: 벤더 + 프렌즈 *(여기서 '프렌즈'는 벤더 미소속 크라우드소싱 = **DP-FA**를 의미)*

| 구분 | 벤더 | 프렌즈 (DP-FA) |
|------|------|--------|
| 모델 | 계약 기반 | 크라우드소싱 |
| 공급 안정성 | 사전 플래닝 기반 **안정 공급** | 예측대로 존재하는 pool 아님, **변동성 큼** |
| 실시간 조절 | **불가** | **가능** (원가 다이나믹) |
| 원가 | 계약 기반(안정) | 변동성 큼 |
| 역할 | **안정 기반** | **버퍼** |

> 예측이 항상 100% 정확할 수 없으므로 → **일정 비율은 벤더로 안정 기반**을 만들고, **일정 비율은 프렌즈로 버퍼**를 둔다.
> **벤더:프렌즈 목표 구성비**는 **변화관리의 영역**이며, **초기 목표는 5:5**로 설정.

**주간 반복 활동**: 차주 물량 예측 → 필요 공급량 예측 → 공급 pool 구성비 결정 → 벤더별 실적 리뷰를 통한 교체·추가 발주 판단.

### 운영 SOP — (3) 상점 CX

| 구분 | 내용 |
|------|------|
| **AS-IS** | 위탁지점이 영업·클레임 해결·배차를 모두 수행 → 상점의 **위탁지점 의존도 큼**. 위탁지점도 본인 영업 상점을 "본사 물량"이 아닌 **"본인 상점"**으로 인식 |
| **TO-BE** | 본사가 영업도 하고 물량 발주도 매주 성과에 따라 조절 → **상점 CX SOP 신규 필요** |
| **대처 SOP** | 우천·기상 악화·기사 부족 등으로 배차 지연/대처 필요 시 **본사가 대처할지 등**을, 상점 / 수행기사(벤더) / 프렌즈 / 본사 간 **새로운 관계성에 맞춘 SOP** 필요 |

## 동대문 테스트 회고 — 주요 이슈 *(지난 2주, ~2026-06)*

> 첫 테스트 지역(동대문구)에서 실제 운영하며 드러난 문제들. SOP·플래닝 보완의 근거.

### 1. 초기 진출계획의 틀어짐
- 영업/운영 간 협의가 완료된 권역이 **테스트 시작 직후부터 삐걱** → 지속적 수정/조정 필요
- 추정 원인: 영업·운영 모두 너무 야심차고, **서로에게 좋은 사람이 되려** 가능하다고만 함 (낙관적 합의)

### 2. 첫 S&OP의 실패
- **물량 예측**: 구조 변환 이전 물량 기반 예측 자체는 크게 안 틀림. 단, 영업조직이 **신규 영업 상점 물량을 과다 예측**
- **공급 구성 의도**: 초기 벤더:프렌즈 5:5 목표. 테스트 전까지 프렌즈만으로 해당 지역 물량을 처리하려 **많은 재원 투자**, 첫 벤더 테스트라 **프렌즈 버퍼를 크게** 두고 싶었음
- **플래닝**: 50%를 벤더로 처리하려면 사전 설정 **1 Set = 벤더 1개**만 계약하면 됨
- **실제**: 운영측이 **벤더 3개 계약 → 3 Set 분 기사 투입** (과다)
- **결과 연쇄**:
  - 과다 기사 + **벤더 우선 배차 로직** → 프렌즈에 제안된 오더 거의 없음 → **프렌즈 대거 이탈**
  - 벤더 3개 중 2개 사실상 이탈 (사유: **배차 엔진 만족도** + **후불결제 적응 이슈**) → **버퍼 역할 할 프렌즈 부재** → **SLA 붕괴**
- **과다 계약의 원인**: 1벤더/1세트로 플래닝했으나 운영은 3벤더/3세트로 진행 → **계획-실행 간 커뮤니케이션 단절**
- **프로모션**: 별도 기획조직 oversight 없이 운영조직이 직접 진행 → 비효율

### 3. CX SOP의 부재
- 벤더 기사(플랫폼사 오더만 경험)가 **배달대행 특유 오더 특성(후불결제 등)에 적응 못함**
- 배달대행만 쓰던 상점은 배송 이슈 시 본사 콜센터가 아닌 **영업사원·기사에게 직접 항의**
- 전투배차(오더 생성 즉시 배차)에 익숙한 상점은 **픽업 임박 시점에 배차하는 AI배차**에 불만
- 시스템 기반 운영이 목표였으나 **초기에는 사람 손이 많이 듦**

### 4. 기타
- 사전 준비가 필요했으나 놓친 프로세스 다수 → 시간 소요 (예: **주간 정산서 작성**)
- **후불결제는 프렌즈 불가 (시스템상 제약 — 프렌즈 앱에 후불결제 모듈 미구현)** → 벤더 기사가 처리해야 했으나 미숙 → 문제 빈발

### 핵심 학습 (초안)
- 영업·운영 합의에 **낙관 편향** 존재 → 진입 전 검증 장치 필요
- **계획-실행 간 커뮤니케이션 단절**(1벤더 계획 → 3벤더 실행)이 공급 과다의 직접 원인 → 플래닝-실행 핸드오프 규율 필요
- **벤더 발주량 + 벤더 우선 배차**가 프렌즈 버퍼를 잠식 → **발주량 통제 = 버퍼 유지**의 핵심 레버
- **후불결제 오더는 현재 프렌즈(DP-FA)로 커버 불가** (시스템 제약, 프렌즈 앱 모듈 미구현) → 모듈 구현 전까지는 벤더 의존이 불가피
- CX·정산 등 **지원 SOP의 선제 수립** 필요

## 개선 방향 *(이번 경험 기반, So What)*

### 1. 초기 진출계획 — 더 촘촘하게
- 권역기준을 **영업/운영이 더 확실히 상호 약속**하고 설계
- **야심찬 접근 대신**, 장기적으로 상황을 보며 **점진적으로 확대**하는 계획으로 접근
- 판/원가·운영시간·권역 외에 **추가 사전 고려**: 우천 시 축소할 **1·2차 예비 권역**, **배상정책**, **재이동·반납 요율** 등

### 2. 초기 S&OP — 더 보수적·체계적으로
- 오픈 **첫 주는 최소 세트 수준**으로 운영 목표 → 1주간 **이슈 탐지·해결 집중** 후 **점진적 상점 오픈**
- 원래 계획한 **S&OP를 실제로 주간 실행** (동대문은 각자 이슈 대응만 하고 S&OP를 추가 진행 안 해 → 간극 확대)
- 본질(시스템 기반 운영)로 회귀하기 위해 **물량 예측 + 영업 목표/현황 공유 강화**
- 벤더에 **명확한 성과/보상 기준을 강하게 적용**, **시간대별 슬롯 설정을 더 촘촘히**

### 3. CX SOP — 본격 구축
- 개인기가 아닌 **시스템 기반 공통 프로세스**로 운영
